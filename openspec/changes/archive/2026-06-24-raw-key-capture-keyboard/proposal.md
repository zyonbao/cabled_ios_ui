## Why（最初设想）

当前「键鼠操作」的键盘输入依赖**宿主（Mac）端输入法**：普通字符与中文都先在宿主 IME 组合，完成后才以 `send_keys`（文本输入）发送到设备。设想做一个「原始按键模式」，像真实蓝牙硬件键盘那样**逐键捕获并发送到设备，由设备端输入法组合中文**（敲 `n i h a o`，由 iOS 端拼音键盘组合）。

## 调研结论（为什么不做）

**核心前提不成立**：在 WDA / XCUITest 工具链下，无法让设备端 IME 对注入的按键进行组合。

- iOS 键盘输入分层：HID 层 → 硬件键盘/IME 组合层 → 文本输入层。**IME 拼音组合引擎只挂在「硬件键盘」那条流水线上，且只有从底层 HID 真正进来的输入才会经过它。**
- WDA 的三条通道（`send_keys`/typeText、`key_chord`/typeKey、`key_event`/W3C key）**全部是 XCUITest 在上层合成的事件**，没有一条是底层 HID 注入。`typeKey` 能让 ⌘A 这类**键盘命令**生效、也能把单字符敲进去，但它**绕过了 IME 组合层**——字母以「字符插入」落地，设备端拼音**不会**把它们组合成中文。
- 要实现「设备端 IME 组合」需要注入真正的 HID 键盘报文，这在 USB / WDA 路径下**无法获得**（iOS 无公开 API）。

**剩余价值不足以支撑实现**：
- 中文（真正痛点）：无解——宿主 IME 组合后发文本，几乎是 WDA 体系下 iOS 真机中文输入的唯一可行方式。
- 英文 / 数字 / 符号：现有「文本模式」已可正常输入，且 `send_keys` 是**批量**发送；逐键反而**每键一次 HTTP 往返、更慢**。
- 快捷键 / 组合键 / 导航键：现有 `key_chord` / `key_event` 路径**已覆盖**。

## 结论

不实现「原始按键模式」。现有「宿主 IME 组合 + `send_keys`」对中文是既有最优解；英文/快捷键现状已满足。如未来出现可用的底层 HID 注入手段（例如设备端配套组件），可重新评估。

## Impact

- 无：不改代码、不改 spec、不新增依赖。
